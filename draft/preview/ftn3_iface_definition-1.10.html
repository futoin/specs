1. Basic concept

1.1. Peer-to-peer communication

There are Invoker and Executor sides. Both can be implemented within the scope of a single process, across different processes, or across different machines over a network.

Multi-peer communication is assumed to be a higher-level concept built on top of the current one.

Object-oriented remote calls are also assumed to be a higher-level concept.

It is assumed that there is a language- and/or platform-specific standardized low-level API/ABI for establishing connections and making calls, coupled with an optional standardized high-level binding/mapping of FutoIn interfaces to native language features.

All specifications and implementations are assumed to support loose coupling of each component, making them suitable for easy separation, replacement, and unit testing.

Each call has a request message and may have a response message containing the key-value pairs described below. If a call does not expect to return any result, no response message must be sent or expected. It must be possible to override this behavior using the forcersp flag in the request message.
Note: This means a call must return at least something to allow the Invoker to detect whether the call was executed properly.

For large data transfer efficiency, if the message transport allows such extensions, a request message can be coupled with raw request data and/or a response can be replaced with raw response data. A typical scenario is a file upload and/or download via HTTP(S).

The lower-level message exchange protocol is out of the scope of this specification.

Possible examples of Peer-to-peer communication types:

  • Raw datagrams (e.g., UNIX Domain Sockets, UDP, or SCTP)
  • WebSockets
  • HTTP with the request in POST and response in the body
  • HTTP with the request in the GET path with parameters and response in the body
  • HTTP with the request in POST or GET and a non-message payload in the body (e.g. BLOB)
  • HTTP CRUDL mapped to/from a FutoIn interface

1.2. Function Call

The major components are: function identifier, parameters, result, and exception.

  • function identifier - A unique associative string containing the interface name, version, and interface function encoded within it.
  • parameters - Key-value pairs:
    • key - Unique associative string name.
    • value - Value of an arbitrary JSON type defined in the interface.
  • result - Key-value pairs, structured similarly to parameters.
  • exception - Associative name of the first error that occurred during function execution.

1.3. Client-server/service multiplexing mode

The Invoker is responsible for enabling request message (and consequently response message) multiplexing by adding a special request ID field: rid. The Executor is responsible for echoing the exact same field back in the related response message.

Please note that Invoker and Client, as well as Executor and Server, are NOT synonymous terms. The Client is the peer that initiated the peer-to-peer communication channel. The Server is the peer that accepts peer-to-peer communications. On the other hand, an Invoker sends a request and an Executor replies to it.

Client-side request IDs must be prefixed with "C". Server-side request IDs must be prefixed with "S". Events, also client-side requests, musst be prefixed with "E".

The rest of the request ID should be an integer value starting at 1 and incrementing with every subsequent request sent. However, implementations should allow adding other custom prefixes to this value.

Note: A Request ID must never be used outside of a multiplexing context, as it is, by definition, duplicated across different communication channels.

1.4. Uni-directional call pattern

The Invoker/Executor side is semantically defined and does not rely on the Client/Server status of the peer. There is no protocol-level support for enforcing this relationship; each side controls whether it can act as an Executor.

It is recommended that the Client side always acts as the Invoker in a uni-directional pattern.

Both serial and multiplexing modes are permitted.

1.5. Bi-directional call pattern

Each side acts as both Invoker and Executor. The bi-directional pattern must always operate in message multiplexing mode.

1.8. Parameter and result types

Standard FutoIn interface types are semantic types first of all. Those define requirements for value types and their ranges. Specific on-wire format can be different with fallback to one or another string representation as the absolute minimum.

  • boolean - true or false
  • integer - Signed integer with the default 32-bit precision.
    • See custom type constraints for other integer classes.
  • number - Floating-point value with the default 32-bit precision.
    • See custom type constraints for other floating-point classes.
  • decimal - a decimal number with fixed number of digits and fixed decimal point position, precision and scale correspondingly.
    • See custom type constraints for mandatory configuration classes.
    • Implementation may impose restrictions on maximal supported ranges.
  • datetime - a collection of different date, time, timestamp and duration classes. The the mandatory custom type constraints.
  • string - String of unlimited length.
  • map - Key-value pairs (effectively a JSON object). No ordering is guaranteed.
    • key - String.
    • value - Any type defined in this section.
  • array - Ordered list of values.
    • value - Any type defined in this section.
  • enum - Value from a predefined set.
    • value - Integer or string.
  • set - List of unique values.
    • value - Integer or string.
  • data - Binary data.
    • value - Sequence of bytes.
  • any - Field type is not validated.
  • CustomType - Any custom type defined, inherited, or imported within the same interface.

Note: null can be used only as a placeholder in "default" values.

1.8.1. Custom types

Each interface can define its own types in the optional "types" field.

Custom types are inherited and imported. Redefining an existing type in such cases is an error.

Each custom type must be based on one of the standard types, but can define various optional constraints:

  • integer:
    • min - Minimum allowed value, integer (inclusive).
    • max - Maximum allowed value, integer (inclusive).
    • class - Defines strict integer class and adjusts default min and max constraints therefore:
      • int8 - 8-bit signed integer;
      • uint8 - 8-bit unsigned integer;
      • int16 - 16-bit signed integer;
      • uint16 - 16-bit unsigned integer;
      • int32 - 32-bit signed integer - the default;
      • uint32- 32-bit unsigned integer;
      • int64 - 64-bit signed integer;
      • uint64- 64-bit unsigned integer;
      • reserved: int128 - 128-bit signed integer;
      • reserved: uint128- 128-bit unsigned integer;
      • reserved: int256 - 256-bit signed integer;
      • reserved: uint256- 256-bit unsigned integer;
      • The reserved classes are not required by the current specification, but those can be implemented as an optional feature.
  • number:
    • min - Minimum allowed value, floating-point number (inclusive).
    • max - Maximum allowed value, floating-point number (inclusive).
    • class - Defines strict integer class and adjusts default min and max constraints therefore:
      • reserved: float16 - 16-bit IEEE 754 binary floating-point number;
      • float32 - 32-bit IEEE 754 binary floating-point number - the default;
      • float64 - 64-bit IEEE 754 binary floating-point number;
      • reserved: float128 - 128-bit IEEE 754 binary floating-point number;
      • reserved: float256 - 256-bit IEEE 754 binary floating-point number;
      • reserved: bfloat16 - alternative 16-bit floating-point number;
      • The reserved classes are not required by the current specification, but those can be implemented as an optional feature.
  • decimal:
    • min - Minimum allowed value, number or decimal-as-string (inclusive).
    • max - Maximum allowed value, number or decimal-as-string (inclusive).
    • class - Defines decimal number constraints, string:
      • p.s, where p is total precision in decimal digits as positive integer, and s is scale (digits after point) as non-negative integer.
  • datetime:
    • min - Minimum allowed value, value-as-string (inclusive).
    • max - Maximum allowed value, value-as-string (inclusive).
    • class - Define class of data and time-related storage, string:
      • date - timezone-agnostic RFC 3339 date in "YYYY-MM-DD" format;
      • time - timezone-agnostic RFC 3339 time in "HH:mm:ss" format;
      • timestamp - UTC time as in RFC 3339 "YYYY-MM-DDTHH:mm:ssZ" format;
      • duration - RFC 3339 duration format with leading "P";
      • period - RFC 3339 time period format variants with "/" separator, only start and end timestamp is allowed due to known ambiguity of duration on large values;
      • NOTE: date, time and timestamp must always use the full format, all classes must never use fractional part and always "Z" UTC zone.
  • string:
    • regex - ECMAScript regular expression.
    • samples - Array of samples to validate backward compatibility of regex in derived specs (revised, inherited or imported).
    • minlen - Minimum string length, integer (inclusive).
    • maxlen - Maximum string length, integer (inclusive).
  • array:
    • minlen - Minimum array length, integer (inclusive).
    • maxlen - Maximum array length, integer (inclusive).
    • elemtype - Required element type.
  • map:
    • For schema structure:
      • fields - A map of field names to:
        • type - Required field type
        • optional - Optional boolean. true if the field can be omitted.
        • desc - Optional string description of the field.
    • For key-value mapping (the default):
      • elemtype - Optional mapping value type constraint, default to an unconstrained any (implicit).
      • keytype - Optional mapping key type with constraint for string or enum, the default to is unconstrained string (implicit).
      • minlen - Minimum array length integer (inclusive).
      • maxlen - Maximum array length integer (inclusive).
  • enum:
    • items - List of allowed integer or string values.
    • class - defines storage constraint for some binary encodings.
      • value - the historical default pass by value;
      • string - pass by value as strings, the most compatible;
      • one of integer values for class - pass by items position.

  • set:

    • items - Complete set of allowed integer or string values.
    • class - defines storage constraint for some binary encodings.
      • value - the historical default pass by value;
      • string - pass by value as strings, the most compatible;
      • reserved: one of integer values for class to pass set value by items position as array of integers of specific storage size.
      • reserved: bitset - use items position for bit positions in a bitset of array of uint8 storage requirement;
      • The reserved classes are not required by the current specification, but those can be implemented as an optional feature.

  • data:

    • minlen - Minimum byte length integer (inclusive).
    • maxlen - Maximum byte length integer (inclusive).

NOTE: An omitted optional field of a custom map type must be set to null on incoming messages (requests for the Executor and responses for the Invoker). Optional fields must also be permitted to be sent explicitly as null.

Common Sense constraints:

  • min must not be greater than max.
  • min and max ranges must be sound with storage class constraint.
  • minlen must not be greater than maxlen.
  • Neither minlen, nor maxlen, can be less than 0.
  • enum and set require mandatory items attribute.
  • There is no viable option to ensure regex compatibility except for its presence and opportunistic sample checks.
  • The optional type constraints cannot be applied on top of a type variation, but they can be applied to the individual types inside such variation.
  • datetime type must hold valid date and/or time value.
  • min and max for datetime must sound with its class in general.
    • In case of period, the constraints must be of timestamp class.
    • There obvious limits on the date and time values that can be represented.

1.8.2. "null" parameter value

As a special case, any parameter can be marked with a default value of "null". Beyond providing a default value, this triggers special parameter verification logic that bypasses constraint validation if the actual provided value is null.

1.8.3. Shortcut for type definition

Parameters, result variables, fields in a map, and types can be defined using a simple string representing a known type name.

For example: "param" : "integer" is equivalent to: "param" : { "type" : "integer" }

1.8.4. Type variations

Occasionally, a single parameter or result field may accept multiple distinct types. For example, a database query might return either integer or string field data.

To support this, the specification permits listing multiple types in an array. This approach is supported exclusively in shortcut type definition form, e.g.: "param" : ["integer", "string"]

Since: v1.6

1.8.5. Result type

Functions frequently return a single scalar value. Wrapping single-value results in an object leads to redundant access paths like result.result. Therefore, results may be defined as a string referring directly to a standard or custom type.

Type variations are not allowed in result type definitions.

Since: v1.7

1.8.6. Binary "data" type

Although the original intent was to exclude raw binary data in favor of explicit encodings, supporting the "microservice as library" concept requires native handling of binary data. FutoIn supports raw binary data for efficient in-process calls and binary-friendly codecs.

If an interface uses binary data, it should include the "BinaryData" requirement. An alternative interface or function can be provided to support text-only protocols.

Since: v1.9

If "data" field is used in the interface with a text-friendly encoding, the data field must be automatically encoded in Base64 as a string. The receiving peer must either expect that or use full-featured FutoIn runtime, which would do decoding from the string to binary according to the interface spec automatically. It it strongly advised to use URL-friendly Base64 alphabet, but compliant implementation must be able to decode any Base64 variant with padding and without that.

Due to the above, "BinaryData" interface constraints is not a requirement for "data" type anymore.

Since: v1.10

1.9. Errors and exceptions

Any function call can produce expected or unexpected errors. This concept is analogous to checked and unchecked exceptions in Java.

All expected exceptions/errors that occur during standard execution flow must be enumerated in the throws clause of the function declaration inside interface definitions (see below).

Unexpected exceptions/errors are generated by the execution environment/runtime in response to error conditions unrelated to the logic of the specific function (e.g., internal communication failures, resource limit breaches, crashes, etc.).

Where possible, language/platform-specific bindings should enforce that the Invoker explicitly checks for all declared expected errors.

1.9.1. Predefined unexpected errors

  • ConnectError - Connection error occurring before the request is sent. Must be generated only on the Invoker side.
  • CommError - Communication error occurring at any stage after the request is sent and before a response is received. Must be generated only on the Invoker side.
  • UnknownInterface - The requested interface is unknown. Must be generated only on the Executor side.
  • NotImplemented - The interface function is not implemented on the Executor side. Must be generated only on the Executor side.
  • NotSupportedVersion - The requested interface version is not supported. Must be generated only on the Executor side.
  • Unauthorized - The Executor's security policy prohibits access to the interface or specific function. Must be generated only on the Executor side.
  • InternalError - Unexpected internal error on the Executor side, including internal CommErrors. Must be generated only on the Executor side.
  • InvokerError - Unexpected internal error on the Invoker side unrelated to CommErrors. Must be generated only on the Invoker side.
  • InvalidRequest - Invalid payload passed as a FutoIn request. Must be generated only on the Executor side.
  • DefenseRejected - Security defense systems triggered a rejection. Must be generated on the Executor side, but may also be raised on the Invoker side.
  • PleaseReauth - Executor demands user re-authentication. Must be generated only on the Executor side.
  • SecurityError - The sec request section contains invalid data or requires a SecureChannel. Must be generated only on the Executor side.
  • Timeout - Timeout occurred during any execution stage. Must be used only internally.

1.10. Payload size safety limits

Both request and response messages are assumed to be relatively small. Heavy data should be transferred as raw payload via HTTP or other lower-level protocols. Therefore, a default safety limit of 64 KBytes is enforced for any payload type. Both Invoker and Executor must enforce this limit unless an efficient mechanism with $O(1)$ complexity is used to transfer messages between peers (e.g., shared memory).

1.10.1. Max message size adjustment per function definition

In cases where transferring larger payloads directly in the primary message exchange protocol is necessary, limits can be adjusted per function using the maxreqsize and maxrspsize attributes.

However, this practice is discouraged, as it may compromise service stability.

Supported units:

  • 'B' - Bytes
  • 'K' - Kilobytes (1024 bytes)
  • 'M' - Megabytes (1024 kilobytes)

Since: v1.8

1.11. On Behalf Of calls

Executors are expected to pass authenticated user information in downstream sub-calls so that all authorization checks are evaluated against the end user rather than the Executor service itself. This mechanism simplifies access control implementations in nested service topologies. If a sub-call is intended to execute with service-level credentials, this must be managed via the System Invoker interface options.

Since: v1.3

A set of predefined optional field names is available, but the obf object is extendable with custom metadata by design. Edge executors must ensure that the field is rejected for security reasons, except for some custom designated metadata, which cannot compromise system's security model. All field values must be of string type.

Predefined optional fields:

  • lid: for local service user IDs;
  • gid: for global/federated user IDs;
  • slvl: for original security level as identified by the edge Executor;
  • token: for JWT and similar original tokens passthrough;
  • trace_id: for correlation IDs defined by edge Executors.

Since v1.10

1.12. Minimum user authentication security level

Each function can define a seclvl attribute specifying the minimum required user authentication security level. This governs user validation rather than access control (e.g., sensitive operations may mandate two-factor or public-key authentication). A security level mismatch must trigger a PleaseReauth error, with the first word of the error description specifying the required security level.

All unrecognized security level identifiers must be treated as requiring the maximum level of security.

1.13. Message encoding formats

The appropriate message format highly depends on the context. When both peers are controlled by the same System, the message encoding format can be chosen arbitrary.

When message transport supports additional characteristics like headers in HTTP or message brokers, the message format can be identified by media type headers.

Otherwise, automatic handling of message encoding format must be used as defined in section 1.13.2.

1.13.1. Media types

The officially registered media types start with application/vnd.futoin+ prefix. Those are preferred when other use case constraints do not impose limitations. Compliant implementation should support all listed types for message encoding detection.

The following officially registered by IANA media types are:

  • application/vnd.futoin+cbor - for CBOR-encoded messages;
  • application/vnd.futoin+json - for JSON-encoded messages;

to be registered:

  • application/vnd.futoin+avro - for Avro-encoded messages;
  • application/vnd.futoin+msgpack - for MessagePack-encoded messages;
  • application/vnd.futoin+protobuf - for Protobuf-encoded messages;

The fallback list in case of external constraints:

  • application/avro - for Avro-encoded messages;
  • application/cbor - for CBOR-encoded messages;
  • application/json - for JSON-encoded messages;
  • application/msgpack - for MessagePack-encoded messages;
  • application/protobuf - for Protobuf messages;

Not registered media types, which have been used and listed in FTN5 spec:

  • application/futoin+cbor for CBOR-encoded messages.
  • application/futoin+json for JSON-encoded messages.
  • application/futoin+msgpack for MessagePack-encoded messages.
  • application/futoin+ as prefix for other formats not defined here.

1.13.2. Message automatic format handling

Invokers and Executors may support different sets of message serialization formats. Whenever a format mismatch occurs, the Executor must respond with a JSON-encoded error. The Invoker must then automatically fall back to JSON encoding for all subsequent requests.

Auto-detection of message serialization formats follows these rules (when the message begins with ASCII):

  1. { - Use JSON;
  2. CBOR - Use CBOR;
  3. MPCK - Use MessagePack;
  4. PBUF - Use ProtoBuf;
  5. AVRO - Use Avro;
  6. Otherwise, fall back and attempt JSON parsing.

1.13.3. JSON

JSON is defined in ECMA-404.

JSON encoding must be supported by all standard Invoker and Executor implementations. Implementations for resource-constrained embedded devices may omit JSON support provided there is a clear justification based on size reduction.

Because every FutoIn message is a JSON object, messages must start with the ASCII character { with no leading whitespace.

1.13.4. CBOR

CBOR is defined in RFC 7049.

All CBOR-encoded messages in auto-detection cases must be prefixed with the 4-byte ASCII string CBOR.

1.13.5. MessagePack

MessagePack is defined in the GitHub spec.

All MessagePack-encoded messages in auto-detection cases must be prefixed with the 4-byte ASCII string MPCK.

1.13.6. Protobuf

Protobuf wire format is defined in the Protobuf Encoding spec. Due to wire-compatibility both v2 and v3 language specifications can be supported.

All MessagePack-encoded messages in auto-detection cases must be prefixed with the 4-byte ASCII string PBUF.

1.13.7. Avro

Avro wire format is defined in the Avro Specification.

All Avro-encoded messages in auto-detection cases must be prefixed with the 4-byte ASCII string AVRO.

2. Interface concept

Executor-side function identifiers are grouped into interfaces defined using FutoIn format specifications (referred to individually as a "spec" or collectively as "specs").

All specs used in a system should be available to both Invoker and Executor for dynamic retrieval from specialized repositories over the network. Repository access structures are described later in this document.

For performance and reliability, specs may be pre-bundled or embedded directly within Invoker and Executor applications.

Interfaces must be defined in a machine-readable JSON format. While generic JSON Schema specifications exist, they are too flexible for strict interface definitions. FutoIn therefore defines its own structured JSON schema for interface specifications below.

2.1. Interface definition schema

Using JSON-SCHEMA:

Schema: futoin-interface

    {
        "title" : "FutoIn interface definition schema",
        "type" : "object",
        "required" : [ "iface", "version", "ftn3rev" ],
        "additionalProperties" : false,
        "properties" : {
            "iface" : {

2.2. Naming convention

All identifiers consist of alphanumeric ASCII sequence with the first symbol being a letter. Additional symbol and letter case is defined by the identifier type below. Such additional symbols can appear only in the middle of the identifier. Separate identifier formats have been introduced on purpose to distinguish type of identifiers and prevent name clashing. All identifiers are case-sensitive.

2.2.1. Interface identifier

An interface identifier (name) is assumed to be unique and consists of several string tokens joined by dot (.) separators. Each token must be a lowercase alphanumeric ASCII sequence.

Example: "futoin.event.receiver", "futoin.event.poll"

The first token of the identifier must reference a related domain name or be sufficiently unique to prevent name collisions (e.g., trademarks or registered namespaces). Java package naming convention is highly suggested as the guideline.

Example: "com.example.interface", "org.example.namespace.interface"

Note: The "futoin." interface prefix is reserved exclusively for official FutoIn project specifications.

2.2.2. Function identifier

Function names follow camel case (camelCase) formatting with alphanumeric ASCII characters.

Example: "someFunc", "anotherFunc2"

Note: The "futoin" function prefix is reserved for internal system functions.

2.2.3. Parameter/Result identifier

Parameter and result variable names follow snake case formatting (small_caps_with_underscore) with alphanumeric ASCII characters.

Example: "some_param", "some_result_value2"

2.2.4. Event identifier

In addition to regular camel case functions names, events can be named as upper-case snake case with alphanumeric ASCII characters.

Example: "SOME_EVENT", "OTHER_EVENT_2"

2.3. Interface inheritance

Domain-specific interfaces often share a large set of common functionality and require only a few extra functions or parameters.

An interface can inherit from another interface. It must be possible to call any derived interface through its parent or grandparent interfaces.

2.3.1. Derived and Base interface compatibility rules

There are three cases of derived specifications:

  1. When a new new minor version of the spec is revised.
  2. When inherited as the base of the spec.
  3. When imported as a mixin into the spec.

The following compatibility rules exist:

  1. Type compatibility is controlled based on function parameters and result variable using the base builtin types, ignoring the type names.
  2. For function parameter types:
    • new function parameters can be added only with mandatory default value;
    • types of existing parameters, fields and elemtype can be extended with type variants;
    • fields can defined only additional optional fields;
    • the min, max, minlen and maxlen attribute range can only expand;
    • the storage class constraint cannot change;
    • the regex can become only more permissive;
    • all samples of the base spec must pass regex of the derived spec;
    • the items can only expand;
    • the changes must not alter the call semantics;
    • Invoker may skip sending default values in parameters or send explicit null, but it is now encourage to send the defaults to minimize possible errors and for easier integration of third-party technologies;
    • Executor must ensure that the missing parameter values are substituted with the defaults before such requests are passed to the corresponding service implementation.
  3. For function result variables:
    • new results variables can be added;
    • types of existing result variables, fields and elemtype cannot change to incompatible representation as defined below;
    • fields can defined additional mandatory or optional fields;
    • the min, max, minlen and maxlen attribute range can only narrow down;
    • the storage class constraint cannot change;
    • the regex attribute can only become more restrictive;
    • all samples of the derive spec must pass regex of the base spec;
    • the items attribute can only shrink;
    • the changes must not alter result semantics; . Invoker must expect unknown result variables to appear.
  4. New functions can be added with no restriction.
  5. For function attributes:
    • The rawupload flag must not change.
    • The rawresult flag must not change.
    • The maxreqsize must not decrease.
    • The maxrspsize must not increase.
    • The seclvl must not change.
  6. The requires constraints cannot be more restrictive for inheritance, and must not change in general, but those can change for import mixins.
  7. The order of definitions in params, results, type fields and type items must not change for specs using FTN3 revision 1.10 and above. The order of funcs, types, imports must not affect positional encoding.

Note: Multiple interface inheritance is not supported at this time.

2.3.2. Inheritance conflict resolution in Executor

Due to how Executors handle interface lookup, a single base interface must not be inherited by multiple derived interfaces within the same Executor instance. The primary purpose of inheritance is to establish reusable base implementation logic that can be extended by a single derived interface.

If only an interface's definitions should be reused without sharing implementation logic then the mixin/import feature should be used instead.

2.4. Interface operation requirements

Interfaces can enforce runtime requirements using the requires attribute.

Standard requirement options:

  • AllowAnonymous - The interface accepts calls without Client Authentication details.
  • SecureChannel - Message transport must occur over an encrypted channel to protect sensitive payloads. Channel encryption is the joint responsibility of the Client and Service implementations.
  • BiDirectChannel - Transport channels must support bi-directional message exchange (allowing both peers to act as Invokers and Executors).
  • MessageSignature - Mandates payload signatures for all messages (e.g., HMAC).
  • BinaryData - Mandates binary-friendly transport protocols and codecs (e.g., CBOR instead of JSON).

To maintain security, inheriting interfaces must explicitly re-declare all requires directives defined by parent interfaces.

2.5. Interface repositories

All publicly released specifications must be hosted in an accessible repository containing two identically structured directory trees: "draft" and "final".

Each tree contains:

  • meta/ - Directory containing generated machine-readable data files.
  • preview/ - Directory containing generated HTML renderings of specifications.
  • misc/{spec_name}/ - Optional directory holding assets used to generate the specification.
  • Markdown (.html) specification source files using FutoIn custom extensions.

The meta/ and preview/ folders must follow this naming convention:

  • {interface_name}-{major}.{minor}-iface.json - Explicit version spec definition file (historical versions must be retained).
  • {interface_name}-{major}-iface.json - Pointer/symlink to the latest {minor} version for the {major} release.
  • {interface_name}-iface.json - Pointer/symlink to the latest overall interface version.
  • {schema_name}-{major}.{minor}-schema.json - Versioned JSON Schema file (following the same symlink conventions).
  • {schema_name}-{major}-schema.json - Latest major release schema pointer.
  • {schema_name}-schema.json - Absolute latest schema pointer.

Note: {minor} version numbers must not include the DV prefix.

Note: By convention, specification repository domain names should use the specs. subdomain prefix and be available via HTTP and/or HTTPS.

Automatic retrieval processes must check final/meta/ first before searching draft/meta/. This allows application code to remain unchanged during spec development and after final publication. However, draft specifications remain subject to change without version updates; applications should cache draft specs using short Time-To-Live (TTL) durations or disable caching entirely.

2.6. Iface definition spec version

Every interface definition must specify an ftn3rev field formatted as MAJOR.MINOR. If this field is omitted, FTN3 revision 1.0 is assumed.

Invoker implementations must permit interface loading as long as the major version is supported, regardless of the minor version.

Executor implementations must permit interface loading only if the exact specified FTN3 revision is fully supported.

2.7. Interface mixin

Interface mixins provide a lightweight solution when interface definitions need to be reused across unrelated implementation structures (for example, standard CRUDL patterns).

Mixin interfaces are imported using the imports array containing iface:version string identifiers.

The import procedure handles types, funcs, and requires declarations identically to standard inheritance. However, an imported mixin is not recognized as a parent interface class. See also section 2.3.1.

If an imported interface contains its own imports definitions, these must be treated as if declared directly at the top level of the primary interface. Duplicate imports of compatible interface versions will be merged automatically to resolve diamond-dependency patterns.

2.8. "Heavy" requests

Functions that require significant system resources can be designated as "heavy". Executors may use this metadata to constrain concurrent heavy invocations to protect system stability and performance. Heavy requests may also be assigned longer default timeout thresholds.

2.9. Interface events

Events are seen as special case of functions with optional parameters that return no result. Therefore, those cannot have non-applicable attributes like "result", "rawupload", "rawresult", "maxrspsize", and "throws". Otherwise, there is no principle difference. Events and functions share the same naming space, and follow the same inheritance rules.

Events are designed for storage, and allow special rid field. Unlike the request IDs, the events IDs should be globally unique for storage purposes.

Events should be stored without the forcersp field, sec and obf fields can be stored at implementation discretion based on particular use cases.

Otherwise, "events" is just a semantic alias for clarity, events must be handled exactly the same way as functions.

2.10. Precompiled interface specifications

The complete interface validation and backwards compatibility checking logic is relatively complex and heavy in terms of code size. It is not suitable for all applications. Implementation of such logic in all technologies also raises concerns of excessive duplicate efforts and discrepancies between implementations.

There is a non-mandatory option to support pre-validation and signing of iface definition in JSON format. Such specs should use the special sig field, which must be implementation-defined and not be set manually by interface designer. The signature can be either a sort of checksum or a cryptographic signature encoded in implementation-defined way.

Some technologies cannot maintain JSON field order when parsing. The special itemOrder field must be set only in compiled specs to designate the order, starting from zero.

2.11. YAML support and context information

By design of the interface repositories, the specs are written in Markdown markup and the source of truth interface definitions are defined in such files as embedded JSON code objects. Alternative options are supported.

Another markup approach can be used the implementation. The original interface spec can be coded in YAML, but it must be converted into strict JSON for distribution. YAML must never be supported on the wire.
